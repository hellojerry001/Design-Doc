# 架构与目录

> 这一页属于「指南」板块：讲清楚**怎么用、为什么这么设计**，不罗列参数。

## 文档站由什么构成

```text
docs-site/
├── index.md                    首页
├── guide/                      指南：怎么用、为什么
├── design/                     设计：设计变量 / 图标资源 / 组件预览
├── components/                 组件：单组件 API 与实时预览
├── api/                        接口参考
├── .demo-assets/               示例资产（接自己的项目后删掉）
└── .vitepress/
    ├── config.mts              站点配置（标题、搜索、nav/sidebar 来源）
    ├── nav.mts                 导航树（由 scripts/build-nav.mjs 生成，也可手改）
    └── theme/
        ├── docs.config.ts      ★ 你唯一需要手改的文件
        ├── preview.css         预览区样式（import 真实组件样式）
        ├── assets.generated.ts ⚠️ 脚本生成，不要手改
        ├── assets.ts           通用：组装数据
        ├── gallery.config.ts   组件画廊条目清单
        ├── lib/                通用解析器
        └── components/         UI 部件 + demos/
```

## 四个板块的职责边界

| 板块 | 回答的问题 | 长得像 |
|---|---|---|
| 指南 Guide | 怎么用、为什么这么设计 | 散文 + 架构图 + 目录树 |
| 设计 Design | 长什么样、怎么复现 | 长页面 + 锚点导航 + 可交互预览 |
| 组件 Components | 是什么、有哪些参数 | 一页一个组件，骨架固定 |
| API | 怎么调用、返回什么 | 一页一个接口，骨架固定 |

**为什么必须分离「指南」与「参考」**：参考页是查的（骨架固定、字段齐全、可以无脑翻），指南是读的（有叙事、有取舍）。混在一起会两头不讨好 —— 查的人被叙事打断，读的人被参数表劝退。

## 「文档等于实现」是什么意思

站点里所有可视化页面都在**构建期**解析真实源码：

| 页面 | 数据来源 | 机制 |
|---|---|---|
| 设计变量 | 真实 `.css` 文件 | `?raw` 取原文 → 行级状态机解析 |
| 图标资源 | 真实 JS/TS 常量或 `.svg` 目录 | `?raw` 或 `import.meta.glob` |
| 组件预览 | 真实组件源码 | 运行时 `import()` → 调用工厂函数 |

这样做的好处是：**源码改了，文档自动跟着改**，不存在「文档说 A、代码是 B」的漂移。

代价是：资产必须能被机器读到。如果读不到（比如设计稿还没落成代码），就退到**快照模式** —— 但快照必须在页头标注来源与同步时间，不允许静默使用会过期的数据。

## 接自己的项目

三步：

1. **改 `theme/docs.config.ts`** —— 产品名、板块开关、预览作用域、资产源清单、数据来源标注
2. **改 `scripts/gen-assets.mjs` 里的 SOURCES 清单**，跑 `node scripts/gen-assets.mjs` 重新生成 `assets.generated.ts`
3. **改 `theme/preview.css`** —— import 你项目的真实组件样式

> 第 2 步之所以不能省：Vite 要求 `?raw` 的 import 路径是**静态字面量**，
> 不能拼字符串。所以「读哪些文件」这份清单只能落成真实的 import 语句。
